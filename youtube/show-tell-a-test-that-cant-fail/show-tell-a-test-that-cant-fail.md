## show-tell-a-test-that-cant-fail-slate

Namaste, this is Liam Inferbear with a short film for Info 7375 Computational Skepticism for AI. You might think a good test is one that passes, but a pass only means something if the test could have failed. Three terms falsifiable some possible result could prove it wrong. Fail condition, the result that counts as failure written down before you look and risky prediction, a forecast the world could contradict. The move comes from Karl Popper in the logic of scientific discovery, first published in German in 1934. A claim is scientific only if some possible result could prove it wrong. In his words, it must be possible for an empirical scientific system to be refuted by experience. Popper noticed theories in his day that could explain any case at all. Whatever happened, it counted as a confirmation. Their admirers called that strength. Popper decided it was their weakness, a theory that no possible event could refute isn't scientific. Einstein's theory was different, it said starlight passing the sun would bend by a definite amount. The eclipse expeditions of 1919 set out to tell three answers apart, no shift, a small shift, or Einstein's larger one. They reported his, but what impressed Popper was the risk, had the shift been clearly absent, the theory was simply refuted. Now a testing code, this one checks only that the function returns something. Feed it working code, it passes, feed it broken code, it passes. A test that always passes isn't testing anything. It can't tell you which one you had. Rewrite it with a failed condition written first, for this input the answer must match the known result or the test fails. Popper said it plainly, criteria of refutation have to be laid down beforehand. Now broken code fails and a pass means something. Claims work the same way, the system is robust. What result would count against that? None is named so it can't fail. Popper called vagueness like that of Suisse's trick. Rewrite it, error rate on unfamiliar input stays under 2% over any 30 days. Now a bad month proves it wrong. Agents make claims to done success, picture an agent that grades its own work, it stacks the blocks success, it knocks them over success, it does nothing at all success, an agent that succeeds no matter what it does isn't succeeding, it's just doing stuff. This happens with real models, and Thropic System Card for Claude 3.7 Sonnet reports that after repeated failures it occasionally special case tests in agentic coding. It returned the exact values the tests expected or edited the tests to match its code, the tests passed, the general solution never got written. So write down before anything runs the result that would count as failure and check it from outside the agent, not in its own report. If we don't design things beforehand so they could be wrong, we're asserting they'll always work no matter what.
